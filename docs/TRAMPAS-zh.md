# Tauri v2 + Windows 的陷阱——用血换来的

搭建 winshotx 时发现的四十六个真实 bug。没有一个给出清晰的错误：应用卡死、黑屏或者什么都不做。如果窗口又出了什么怪事，从这里开始查。第 6 个是最糟的，因为它在开发环境里看不到。

## 1. 同步命令冻结整个界面

`#[tauri::command] pub fn algo()` 在**事件循环线程**里执行。如果里面创建窗口，那个创建操作会等事件循环……而事件循环正忙着执行这个命令。结果：标题栏显示“(无响应)”和空白窗口。

**家规：所有命令都是 `async fn`。** 没有例外，即使它们不等待任何东西。注意：带 `State<T>` 的 `async` 命令需要显式生命周期（`State<'_, AppState>`），不能返回未包装的类型，必须用 `Result`。

## 2. 从全局快捷键线程创建窗口也会卡死

同样的问题从另一扇门进来：`tauri-plugin-global-shortcut` 的处理器不能直接打开或关闭窗口。在 `recorder::stop` 里，编辑器的打开是用 `std::thread::spawn` 启动的，让它发生在中立线程上。

## 3. 窗口标签不能复用

关闭窗口是异步的。如果快捷键连续按两次，`WebviewWindowBuilder::new(app, "overlay-0", …)` 会失败并报“已存在具有该标签的窗口”，overlay 就再也打不开了。所以每一轮加一个计数器：`overlay-0-7`、`recorder-8`、`editor-9`。

直接后果：`capabilities` 必须用模式（`"editor-*"`），不能用固定标签，否则那些窗口没有权限。

## 4. overlay 上的第一次点击被 Windows 吃掉

一个出现时不是活动窗口的窗口能收到 `pointermove`（鼠标掠过它），但第一次 `pointerdown` 被消耗在激活它上面了：用户拖拽，什么都没发生。修复方法是在 builder 里用 `.focused(true)`，再加上 `show()` 之后对 `HWND` 调用 `SetForegroundWindow`。

在前端，不能用 `setPointerCapture`：拖拽期间在 `window` 上监听（`pointermove` / `pointerup` / `pointercancel`）。

## 5. 由 `asset:` 协议供给的 canvas 会被污染

放大镜用 `getImageData` 读像素。如果图片直接用 `convertFileSrc()` 加载，canvas 就是跨源的，读取会静默抛出 `SecurityError`：放大镜永远显示 `#000000`。解决办法是用 `fetch` 下载 PNG，传给 `createImageBitmap`，再从 blob 画出来，blob 已经是同源的了。

## 6. CSP 在开发环境不生效，在安装包里让 overlay 变黑

最贵的一个。`"csp": "default-src 'self'; img-src 'self' asset: …"` 看起来完整，但 `connect-src` **没有声明**，所以继承自 `default-src`，也就是 `'self'`。冻结屏幕的 PNG 不走 `'self'`：它走 asset 协议，在 Windows 上是 `http://asset.localhost`。那个 `fetch` 被拦截，overlay 没有背景，用户看到一个黑色矩形盖住整个屏幕。

让它如此阴险的地方：**在开发环境里从来不发生**。页面是 Vite 服务的，CSP 只在 Tauri 提供内嵌资源时才注入。在 `dev` 里测试，正常，发布安装包，应用就坏了。

IPC 走同一条路（Windows 上 `fetch` 到 `http://ipc.localhost`），但那个有安全网：当 CSP 拦截它时，Tauri 回退到 `postMessage` 继续工作，更慢，控制台里有个警告。所以命令有响应而背景没加载：症状看起来像“图片看不见”，而不是“CSP 配错了”。

需要声明的：

```json
"csp": "default-src 'self'; connect-src 'self' ipc: http://ipc.localhost asset: http://asset.localhost blob: data:; …"
```

还有两道防线，因为配置不会被编译，也没人审查：

- `src-tauri/tests/csp.rs` 读取 `tauri.conf.json`，如果有人削减了那些来源就变红。它把旧 CSP 作为测试用例包含进去，证明它会咬人。
- overlay 有第二条路：如果 asset 协议失败，通过 `freeze_bytes` 命令请求 PNG，照样画出来。如果还不行，显示错误并给一个手动退出的出口，8 秒后自己关闭，而不是让屏幕被劫持。

**家规：在 CSP 里动的东西用 `pnpm tauri build` 测试，绝不用 `pnpm tauri dev`。** 注意，光用 `cargo build --release` 不行：那个二进制还指向开发服务器，启动时会报连接错误。

## 7. 签名密钥通过 `TAURI_SIGNING_PRIVATE_KEY` 传递，不是通过它的路径

CLI 文档写了三个变量，编译时只有一个真正有效：`TAURI_SIGNING_PRIVATE_KEY_PATH` 被忽略，构建在最后死掉，在已经生成安装包之后，报「A public key has been found, but no private key」。必须传**文件内容**：

```bash
export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/winshotx.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""   # 密钥生成时没有密码
pnpm tauri build
```

关于更新器，有两件事必须清楚：

- **今天安装的版本决定明天能不能更新。** 装了 0.1.1 的人永远不会知道有 0.1.2 存在，因为他的副本没有更新器。这一步手动跨过去一次就行了。
- **`latest.json` 不是手写的。** 它由 `scripts/publicar.mjs` 从 bundler 刚生成的 `.sig` 生成。一个旧签名粘在里面发布时不会报错：它在用户的机器上失败，在尝试更新的时候，那是你看不到的地方。

## 额外：全局事件撞上死窗口

`app.emit(...)` 试图投递给**所有**窗口，包括刚关闭的，然后抛出 `PostMessage failed … El identificador de la ventana no es válido`。录制栏的计数器因此归零。改成逐窗口发射，遍历 `app.webview_windows()` 并按标签前缀过滤。

## 8. `WebviewWindow::emit(...)` 不是“从这个窗口发射”，是“发射给所有窗口”

在具体实例上调用它（`ventana.emit(...)`）有欺骗性：看起来事件从那个窗口发出、到达那个窗口，但它和 `app.emit(...)` 是完全一样的全局广播（底层共享同一个 `manager()`）。这在 2026 年 8 月 26 日真正咬人了，当时 overlay 从每次截图创建新窗口改成每个显示器复用一个窗口（见 `windows_mgr::open_overlays` 和记忆 `winshotx-overlay-multimonitor`）：用 `ventana.emit(EVENT_OVERLAY_SHOW, payload_de_ese_monitor)` 通知每个复用的窗口有新截图时，**三个**窗口都收到了，最后发射的那个在三个屏幕上同时获胜。

**正确的方式是 `emit_to(etiqueta, evento, payload)`**，把具体窗口的标签作为第一个参数，而不是在一个不同实例上调用一个不同的方法。

**而真正花钱的后半部分：`emit_to` 是必要的，但不够。** Munir 仍然看到他的主屏幕在其他屏幕上重复，在预览里和最终裁剪里。确认了不是任何明显的怀疑：磁盘上的 `freeze-N.bmp` 是正确的（用 Python/PIL 验证过），每个窗口的实际位置和请求的一致，Rust 从正确的屏幕裁剪（`capture/mod.rs` 里有两个测试固定了这一点）。

原因在**另一边**。前端做的是：

```ts
listen(EVENTS.overlayShow, (e) => boot(e.payload))   // <- 没有 target
```

没有 `target` 的 `listen` 注册为 `{ kind: 'Any' }`；包自己在 `@tauri-apps/api/event.d.ts` 里说了：*"The event target to listen to, defaults to `{ kind: 'Any' }`"*。而在 `tauri` 里，`event/listener.rs` 这样决定一个监听器是否接收：

```rust
*target == EventTarget::Any || filter.as_ref().map(|f| f(target)).unwrap_or(true)
```

其中 `target` 是**监听器**的：如果注册为 `Any`，函数返回 `true`，**根本不看过滤器**。也就是说一个 `Any` 监听器完全跳过任何 `emit_to`。三个窗口都收到了 `open_overlays` 循环的三个 payload，各自留下最后一个，所以三个都在画和裁剪同一个屏幕。

**修复方法是在注册时传窗口标签：**

```ts
listen(EVENTS.overlayShow, (e) => boot(e.payload), { target: getCurrentWindow().label })
```

故意传成**字符串**：字符串会转换成 `AnyLabel`，和 Rust 里的 `emit_to(label, ...)` 一样，`manager/mod.rs` 里的 `filter_target` 按标签把 `AnyLabel` 和 `AnyLabel` 匹配起来。两边说同一种语言，不依赖目标是 Window、Webview 还是 WebviewWindow。

**适用于这个应用任何事件的通用教训：** 在 Tauri v2 里，事件的目标由**两边**决定。只限定发射方没有用，如果接收方订阅了一切的话。而 `listen` 的 `target` 看起来是可选的，因为类型把它排除在外了；一旦有多个窗口跑同样的代码，它就不是可选的。

必须到达所有窗口的事件（`overlayMode` 和 `overlayTakeScreen`，模式栏在屏幕间同步的方式）故意不带 `target`。那里广播就是功能，不是 bug。

## 9. `.focused(false)` 不阻止复用窗口抢焦点

定时器倒计时存在是为了能拍到打开的菜单：按下快捷键，打开菜单，三秒后连菜单一起冻结屏幕。如果数字小窗口抢到焦点，菜单就关了，功能就没用了。

`WebviewWindowBuilder::focused(false)` **只在第一次有效**。它是一个构造选项：告诉 Windows 创建窗口时不要激活它。但那个窗口在截图之间不关闭，它隐藏并复用（和 overlay 一样，见陷阱 3），第二次的 `show()` 是一个普通的 `ShowWindow`，会像激活任何其他窗口一样激活它。也就是说：第一次倒计时尊重菜单，第二次把它关掉。

**修复方法是在 HWND 上设置扩展样式，不是构造器选项：**

```rust
let actual = GetWindowLongPtrW(hwnd, GWL_EXSTYLE);
SetWindowLongPtrW(hwnd, GWL_EXSTYLE, actual | WS_EX_NOACTIVATE as isize | WS_EX_TOOLWINDOW as isize);
```

`WS_EX_NOACTIVATE` 是窗口的属性，不是显示时的属性：Windows 永远不再激活它，即使点击它也一样。它住在 `platform::window_style::never_focus`，构造时应用一次。

**注意这意味着什么：** 一个永远不抢焦点的窗口也收不到键盘。所以倒计时期间不能按 Escape 取消，这是故意接受的：替代方案是在那几秒注册一个全局 Escape，那会把它从正在被拍摄的应用那里抢走。

## 10. 新窗口的标签不在 `capabilities` 里就会变哑

`src-tauri/capabilities/default.json` 带一个标签列表（`main`、`overlay-*`、`recorder-*`、`editor-*`...），权限只到达和它匹配的窗口。一个带新标签的窗口**不继承任何东西**：`listen`、`emit` 和窗口调用都失败，而且失败得像 `useEffect` 里的一个 promise rejection，也就是说窗口里看不到任何错误，只有一个不响应的界面。

加定时器倒计时（标签 `countdown`）时必须把它放进那个列表。**新窗口收不到事件时，这是第一个要看的地方**，在怀疑陷阱 8 之前。

## 11. 系统音频：连续四个陷阱

把声音从扬声器取出来放进 MP4 有四个会静默失败的地方。四个都在 2026 年 8 月 27 日关闭 META 2 时出现。

**`windows` crate 把 `IMMDevice::Activate` 藏在名字和你预期不一样的 features 后面。** 开了 `Win32_Media_Audio` 和 `Win32_System_Com`，方法仍然不存在，编译器只说 `no method named Activate found`。还需要 `Win32_System_Com_StructuredStorage` 和 `Win32_System_Variant`，因为激活参数是一个 `PROPVARIANT`。当 COM 的某个方法缺失时，去看 crate 代码里包围它的那个 `#[cfg(all(feature = ...))]`，别猜。

**`WAVEFORMATEX` 是打包的，不允许引用它的字段。** 对它两个字段的 `assert_eq!` 编译不过：`error[E0793]: reference to field of packed struct is unaligned`。先复制到单独的变量里。这不是警告，是错误，而且出现在最蠢的地方。

**Windows 以 32 位浮点交付声音，AAC 编码器要 16 位整数。** 没人抱怨：`send_audio_buffer` 照收字节，MP4 出来是哑的或者带啸叫。转换在 `record::audio::a_pcm16`，在缩放之前裁剪到 [-1, 1]，因为超过 1 的采样在转换时会翻转，听起来像爆音。

**而 `send_audio_buffer` 忽略传给它的时间戳。** 它自己的代码说了（`_timestamp: i64, // ignored to guarantee monotonic audio timing`）：它按收到的采样数放置声音。实际后果：**路上丢的一段声音不留空洞，而是把后面的一切都移位。** 所以 Windows 标记为 `SILENT` 的缓冲区（故意到达时是空的）必须手动填零并照样发送，而不是跳过它们。

## 12. 一张屏幕照片看不到应用说的一半东西

`scripts/ver-ventana.mjs` 拍整张屏幕，用来用眼睛看，但**住在属性里的东西不出现在照片里**。2026 年 8 月 27 日，捕获栏已经用西班牙语说了几周，而应用是英语的，没人看到：它的按钮只有图标，所以它们说的一切都在 `title` 和 `aria-label` 里，两个都不画出来直到有人把鼠标悬停在上面。

只悬停时才出现的东西也一样。测试台现在把 `pointerenter` 和 `pointerover` 发给点的每个祖先（“进入”**不冒泡**，必须一个个发），但即使这样每张照片也只看到一个状态。

**能抓到它的：** 一个把界面挂载成英语并检查 `document.body.textContent` 和 `aria-label` 里没有一句西班牙语的测试。它们在 `SettingsApp.test.tsx`、`ModeBar.test.tsx` 和 `FrameStrip.test.tsx` 里。

从搭建它们得出的规则：**一个从没见过红的测试什么都没证明。** 两个语言测试是通过手动破坏翻译、看着它们失败、再把代码放回去来首秀的。

## 13. OCR 不认手画的字母

文本读取器的第一个测试用粗黑矩形在白底上画「HI」，对人来说毫无疑问能读。`Windows.Media.Ocr` 返回了**空字符串**，有一阵子看起来像引擎不工作。

不是引擎：OCR 是用真实字母训练的，有曲线和可变粗细，直条不像任何字母。好的测试**用 GDI 和系统字体画文本**（`CreateFontW` + `TextOutW` 画在 `CreateDIBSection` 上），这也是最像它将要真正读取的截图的东西。这样它第一次就读出 `"winshotx lee texto"`。

两个 GDI 细节花了一会儿：`BITMAPINFOHEADER` 的 `biHeight` 要**负数**，这样行是从上到下的，这是 `image` 想要的，DIB 的像素是 **BGRA**，不是 RGBA。

还有一个 `windows` crate 0.62 的：等待 WinRT 操作的方法是 **`.join()`**，不是 `.get()`。它是 `IAsyncOperation` 的固有方法，所以不需要导入任何 trait（编译器建议的 `Async` trait 是私有的，不能导入）。

## 14. 数被触碰的像素不是测量笔画

编辑器的标注出来时笔画是**一像素宽**，十三个测试绿。没有一个看到，因为都数同一样东西：有多少像素不再是白的。一个一像素粗的矩形触碰几百个像素，所以计数很高，测试通过。

原因在用来加粗笔画的圆盘抗锯齿：

```rust
// 错：在距离 = 半径处，边缘正好是 0，什么都不画。
let borde = (radio as f32 - distancia).min(1.0);

// 对：测量到半径外半像素。
let borde = (radio + 0.5 - distancia).clamp(0.0, 1.0);
```

用坏的版本，半径 1 的圆盘只画**一个像素**：中心那个。而半径是半像素（笔画 3 的半径是 1.5），所以把它们存成整数会向下取整，让问题更糟。

**能抓到它的：** 一个数边缘上连续绘制的行数、并和它声称的粗细比较的测试。最重要的是，一个 `--ignored` 的测试留下 PNG 供查看。在图像里一眼就看到了；在数字里没有。

和音频、和未翻译文本是同一个教训，换个说法：**一个测量后果的测试不测量那个东西。** 被触碰的像素是粗细的后果，不是粗细。

## 15. `object-contain` 留下条纹，上面的图层不知道

编辑器的预览用 `object-contain` 调整：尽可能大而不变形，在两侧或上下留下条纹。上面是标注层和裁剪层，坐标是**从 0 到 1 在截图上**。

那些图层被拉伸到整个空间（`absolute inset-0 size-full`），所以它们的坐标把条纹也算成了截图的一部分。放在图像边缘的箭头保存时稍微超出了，导出时偏移。**一个垂直截图在宽窗口里，偏移是半张屏幕。**

花了一会儿才找到，因为在正常情况（水平窗口里的水平截图）误差是百分之二，看不出来。

**不管用的：** 在盒子上放 `aspect-ratio`，指望浏览器调整它。在一个有自己的内容的容器里，那个属性的解析方式取决于容器类型：在 `flex` 里子元素取内容的大小，计算变成循环的；在带 `place-items-center` 的 `grid` 里也不行。

**管用的：** 用 `ResizeObserver` 测量空间并手动计算盒子（`src/lib/contener.ts`），它还能不用窗口就测试。通用规则：**如果一个图层必须落在被 contain 的图像上，就测量；不和 CSS 协商。**

## 16. 依赖不完整的按键处理器会关闭窗口

在编辑器里，`Escape` 必须先松开正在做的事（裁剪框、绘图工具），只有在什么都没做时才关闭。关闭编辑器**会丢掉磁盘上的帧**，所以一个无意的 Escape 不能带走一段三分钟的录制。

处理器住在一个 `useEffect` 里，读取那个状态。依赖没更新时，关闭拿着旧快照：它以为什么都没在做，照样关闭。代码读起来完美，做的和说的相反。

还有后半部分：把函数（`cerrar`）放进依赖时，必须检查它已经在上面声明过了，否则整个渲染会崩，报「Cannot access before initialization」，在 React 里看起来像白屏。

一个真正的测试抓到了它：按 `c`，按 `Escape`，检查窗口**没有**关闭。它在 `EditorApp.test.tsx` 里。

## 17. 对路径做 `starts_with` 不能阻止逃出文件夹

一个固定窗口把它的 PNG 路径发给 Rust，用来复制、保存或读取。检查它以固定文件夹开头，看起来足够了，但不够：

```
C:\...\Temp\winshotx\pins\..\..\..\.ssh\id_rsa
```

以正确的文件夹开头，结束在任何它想去的地方。检查必须**拒绝任何 `..` 组件**，不只是看开头。`canonicalize` 也行，但它要求文件已经存在，这里不总是。

在 `commands.rs` 里，有一个对旧代码变红的测试。

## 18. `image::imageops::resize` 每帧要 60 ms，过滤器没有错

Munir，2026 年 8 月 27 日，在 `tauri dev` 里测缩放：*«为什么保存视频这么慢？saving 卡住了»*。

它没卡：它在缩放。**没有缩放时，一个已经达到要求尺寸的帧不缩放，直接过去。** 有缩放时，每一帧被裁到一块然后拉伸到最终尺寸，所以出现了一个以前不存在的缩放，在放大区段的**所有**帧里。

在 640x400 → 1280x800 上测量：

| | release | debug |
|---|---:|---:|
| `image` 用 Lanczos3 | 62 ms | 2.167 ms |
| `image` 用 Triangle | 53 ms | 1.138 ms |
| `image` 用 Nearest | 52 ms | 602 ms |
| **`encode::escalar::ampliar`** | **3,8 ms** | **19 ms** |

**线索是 `Nearest` 和 `Lanczos3` 花一样多。** 如果最笨的过滤器和最精细的一样慢，时间不是花在过滤上：是花在 `image` 为服务任何像素类型走的通用路径上。这里只有一种情况，8 位 RGBA，可以直接走：定点权重表、一个平面循环、用 rayon 分行。

同一个测量还出了两件事：

1. **`opt-level = 3` 不需要，而且试过了。** 第一次尝试是把 `image` 和 `winshotx` 编译成全速而不是小体积。从 91 到 62 ms，但安装包从 2,31 涨到 **2,66 MB**：360 KB 换三分之一的改进。用自己的缩放，同样的代码在 **`opt-level = "s"` 下跑到 2 ms**，也就是说速度来自算法，不是编译器。它被去掉了，安装包保持原样。教训：**为速度付尺寸之前，两个都测。**
2. **在 debug 里，倍数不是 20，是高达 85。** 一个带缩放的一分钟视频在 `tauri dev` 里要四十分钟，在安装版里要两分钟。测性能，用安装版；`dev` 只用来看某个东西能不能工作。

双线性而不是 Lanczos3 **是故意的**：Lanczos3 用于缩小，那里需要把很多像素平均成一个。放大时，它的负瓣在对比边缘留下光晕。缩小仍然用 `image` 的。

## 19. Media Foundation 在最后一个帧结束视频，不是实际结束时

从一个静止屏幕抢救三十秒，得到一个 **66 毫秒**的视频。不是环形缓冲区（会话说 3000 ms，正确的，帧也在），不是播放器：是编码器。

`VideoEncoder::send_frame_buffer(buffer, timestamp)` 说的是每一帧**开始**的时刻，仅此而已。Media Foundation 在它收到的最后一帧之后一个 `1/fps` 结束文件。一千帧的话，最后丢 33 毫秒，看不见。一个静止屏幕，缓存保存成**一个**持续三秒的帧，整个视频就丢了。

**修复：** 把最后一帧发**两次**，第二次在它应该结束的那一刻。和前一帧完全相同，压缩时什么都不占。

**怎么发现的：** 用测试 `el_anillo_traga_la_pantalla_de_verdad`，它真正捕获屏幕并读取写出的 MP4 的 `mvhd` 头里的时长。没有任何合成测试会看到，因为它们都发 33 ms 的帧。看到它的是遇到静止桌面的那个。

导出也一样受影响：一段什么都没动的录制出来是短的。

## 20. 一个看起来没关的关闭按钮就是一个坏按钮

从环形缓冲区抢救出来的东西**在**有预览视频**之前**打开编辑器，预览是在后台写的。播放按钮在那期间被设成 `disabled`，有一个 `title` 解释。即便如此，Munir 按了它，什么都没发生，他当它是坏的：`title` 必须让鼠标悬停不动才能发现，而按钮的 class 里没有任何 `disabled:` 让它变暗。它看起来**完全一样**于一个能用的。

三件事从那里出来，三件都适用于应用里的任何按钮：

1. **没有 `disabled:` 样式的 `disabled` 不存在。** 标注栏的撤销按钮已经有 `disabled:opacity-30`；这个没有。
2. **`title` 不是警告**，是脚注。要等的东西在屏幕上说，如果知道还差多久，带数字。
3. **一个只在某事成功时才发的通知让失败不可见。** «预览已就绪»的事件现在在没出来时也发。

还有同一天的第四件：**`video.play()` 从点击里请求，不是从 effect 里。** 从一个之后运行的 `useEffect` 启动，就落在人的手势之外，浏览器可以拒绝它；而且它返回一个 promise，被一个 `.catch(() => undefined)` 吞了。现在它从按钮自己的处理器里出来，原因也显示出来。

**怎么调查的，为了下次某个东西在 webview 里«不响应»：** Windows 的无障碍树（UI Automation）能读到 Tauri 窗口里控件的真实状态**而不碰它**：`AutomationElement` 按 `ProcessId` 过滤，每个按钮说它的 `Name` 和 `IsEnabled`。这样不用问也不用打开就知道，那一刻按钮已经是启用的，失败是之前的等待。

## 21. 复制到剪贴板从缓存里读，不是从刚导出的东西

Munir 在一张截图上画了个红箭头，点了复制按钮，粘出来：没有箭头。保存的文件有。

`copy_result` 对一个 PNG 做的是：

```rust
let image = record::read_frame(session, request.from)?;   // 原始帧
```

也就是说导出所做的一切都被排除在粘贴之外了：画在上面的标记、裁剪、边框、缩放和点击的缩放。在测试里没注意到，因为导出器的 26 个测试检查的是**文件**，文件是完美的。

**修复：** 复制读取刚写出来的文件。而决定（图像还是文件）和剪贴板调用分开了，在 `que_se_pega` 里，这样能测试它而不碰任何人的剪贴板。那个函数**故意不接收会话**：如果有人又要把像素从缓存里取出来，就需要会话了，测试就不再编译。

**通用教训：** 当一个函数面前有已经做好的结果（一个刚写的文件）以及重做它的方法时，重做的那个是错的。

## 22. 在一个地方修缩放不能修好缩放

陷阱 18 写下了 `image::imageops::resize` 每帧要 60 ms，错不在过滤器，在 crate 的通用路径。写了 `escalar::ampliar` 并放在疼的地方。十一天后，导出一段 50 秒的录制要**两分钟**，在 Munir 的情况（1890x1052，1320 帧）上测出来的分布是这样的：

| 步骤 | 每帧 |
|---|---:|
| 从缓存取帧 | 7 ms |
| **用 `image` 缩到 1280** | **64 ms** |
| 编码和写入 | 17 ms |

也就是说 68% 的时间仍然走同一条老路，因为 `escalar::ampliar` 只覆盖了放大，还有**四个**地方在用 `image` 缩小：`exporter::enmarcar_y_anotar`、`mp4::encode`、`gif::scaled` 和 `marco::enmarcar`。每个都有自己的 `if` 和自己的注释解释为什么那里该用 Lanczos3。

**修复：** 一扇唯一的门，`escalar::a_medida`，它决定是放大、缩小还是两者，是四个地方唯一调用的。导出从每帧 **95,6 ms 到 20,4 ms**：Munir 的两分钟现在是 27 秒。

**教训：** 当一个被测量的问题的解决方案是一个新函数时，工作不在写完它时结束。它在 `grep` 旧函数在热路径里不返回任何东西时结束。一个在快和慢之间选择的 `if` 最终会选择慢的。

## 23. 用整数边界缩小会让字母变细

从 1890 降到 1280，每个输出像素覆盖 1,477 个输入。如果边界用整数除法计算，有时平均**两个**像素，有时**一个**：

```rust
let a = (i * origen / destino) as u32;      // 0, 1, 2, 4, 5, 7, 8...
let b = ((i + 1) * origen / destino) as u32;
```

一个纯色活下来了，一个棋盘出来是灰的，这正是当时那两个测试检查的。但**一张截图里的文字出来时有些字母更细**，因为每一笔落在不同的分配里。一个一像素的网格偏了灰色 128。

**修复：** 按面积分配，带分数权重。每个输入像素按它重叠的部分进入，每个轴的权重正好和为一（舍入给最重的权重，否则图像会越来越亮）。和 Lanczos3 在真实截图上的差异从 1,40 降到 **0,41**（共 255），最差的像素从 201 到 56。

**看到它的测试：** 一个从 1890 缩到 1280 的一像素网格必须保持在灰色的 50 以内。整数边界给的是 128。

## 24. `clipboard_win` 的 `set_string` 在写之前**清空**剪贴板

复制一个视频留下文件（CF_HDROP），这是资源管理器和聊天理解的。但粘到一个文本框里什么都不出现，因为文件不是文本，而应用同时说«已复制»：复制成功了。

把路径也作为文本放进去看起来是一行的事：

```rust
formats::FileList.write_clipboard(&list)?;
formats::Unicode.write_clipboard(&ruta)?;   // 这里文件消失了
```

`FileList` 内部用 `NoClear`，`Unicode` 用 `DoClear`，所以第二次调用清空剪贴板并删掉第一次。之后读它返回 `OSError 1168, no se ha encontrado el elemento`，而两个剪贴板测试同时跑时，一个 `STATUS_HEAP_CORRUPTION`。

**修复：** `raw::set_file_list` 然后 `raw::set_string_with(&ruta, options::NoClear)`。从**另一个进程**验证，这是知道剪贴板留对了的唯一方法：`FileDrop, FileNameW, FileName, UnicodeText, Text`。

## 25. Chrome 不拍摄小于 500 px 的窗口，而且它不说

托盘菜单宽 **284 px**（`tray_menu::MENU_ANCHO`）。用 `pnpm ver --menu --ancho=284` 拍它时，照片右半边是空的：没有版本，没有环形缓冲区开关，没有快捷键。看起来是窗口的 bug。

不是。**Chrome 有大约 500 px 的最小窗口宽度**，所以 `--window-size=284,420` 把页面画在 500 上然后把图像裁到 284。右边的一切都存在，但落在裁剪之外。用 `--dump-dom` 验证了：HTML 里有版本、快捷键和 `role="switch"`。

**怎么拍一个窄窗口：** `--escala=2` 向 Chrome 请求 568 个物理像素，它会遵守，配上 `--force-device-scale-factor=2` 让页面以 284 CSS 绘制。照片出来是双倍分辨率，代表真实窗口。

**差点发生的事：** 我差点通过给一些没有任何问题的 class 加 `min-w-0` 来“修”菜单。改动被回滚了。**在修一张截图里看起来糟的东西之前，必须确认截图拍对了**，而 DOM 是知道这件事的便宜方法：如果数据在 HTML 里，失败的是看的方式。

## 26. 没人读的设置是通过测试的谎言

`play_sound` 在设置屏幕上有版本：保存、启动时读、窗口间同步、有自己的开关。唯一不做的是发声，因为**项目里没有一行查询它**。Munir，2026 年 8 月 30 日：*«而且没有声音 xd»*。

没有东西检测到它：测试检查设置被保存和读取，这正是它做对的事。

**怎么抓到：** 在整个树里 `grep` 每个设置名，看有多少地方用**除了**画它的屏幕和保存它的文件之外。如果是零，那个开关什么都不做。审计了 31 个，只有这个失败。

**修复，为了下次：** `platform/sonido.rs` 用 `include_bytes!` 播放一个内嵌的 WAV，用 `PlaySoundW`，Windows 自带的。零新依赖和 12 KB 安装包。还有一个测试检查 WAV 头，因为 `PlaySoundW` **只懂 PCM**：一个重命名成 `.wav` 的 mp3 不会响，也不会报任何错。

## 27. 靠位置或全文搜索的东西无声地坏

同一天出现同一家族的两个 bug，两个都放了很久没人警告。

**第一个，在 `frontlaxweb/generar-en.mjs`。** 页面的描述住在属性里，不能带 `data-en`，所以用一个表翻译，`ATRIBUTOS`，键是**整句西班牙语**。当安装包大小从 2,2 变成 2,49 MB，三个键不再匹配，英语页面继续提供它的 `description`、`og:description` 和 `twitter:description` **用西班牙语**。那是 Google 在英语标题下面显示的，也是把链接粘到聊天里出现的。

**第二个，在 `scripts/ver-ventana.mjs`。** 为了拍导览，它通过点击*«winshotx»块的第三个按钮*打开。那个块换了行，第三个按钮变成了开机启动的开关：导览不打开，照片拍的是普通窗口，看起来是正确的。

**它们共同的地方：** 两个在没人碰任何东西时都对，两个在一个没提到它们的改动里失败，两个**不产生任何错误**：产生一个看起来好的页面或照片。

2. 在只能比较全文的地方，**一个会站出来的守卫**：`generar-en.mjs` 记录它找到了哪些键，退出码 1 并列出不再出现的。通过故意破坏一个来测试：没有那个测试，一个不跳的守卫和它要抓的 bug 一样哑。

## 28. 无头 Chrome 也不尊重 meta viewport

陷阱 25 的姐妹，同一个教训的另一面：**照片可能是坏的，尽管页面是好的**。

用 `--window-size=390,640` 拍 `frontlaxweb/index.html` 看手机上的页脚时，页面以桌面宽度绘制然后裁到 390 px：内容向右偏，文本被切断。**不是网站的 bug。** 无头 Chrome 自己不应用 `<meta name="viewport">`；那需要真正模拟一个设备，这是 Playwright 或带 `Emulation.setDeviceMetricsOverride` 的调试协议做的。

所以，在那个服务器启动之前，**手机端不用截图确认**：要么模拟设备，要么说没看过。

## 29. 看窗口的工具展示了一个不存在的窗口

`scripts/ver-ventana.mjs --escala=2` 给的不是同一张照片更清晰：给的是**另一个窗口**。它把 `--window-size` 乘以缩放，而那个参数是 CSS 像素，不是物理像素。结果：页面画在 1680x1020 而不是 840x510，内容按它平常的大小出来，半张照片是空白。正好和陷阱 27 的高度 bug 相反，效果一样：以为有多余空间而实际没有。

在准备 Store 截图时看到的，因为一张卡片半张黑画布很显眼。没有那个任务它会一直在那里。

**在同一个工具里，语言也没有完整到达。** `--idioma=en` 只进入假设置，那是主窗口的。编辑器不请求它们：它从 `localStorage` 读语言，在一切之前，为了第一次绘制就正确。所以 `--idioma=en` 给了一个**西班牙语的**编辑器，没有任何警告。现在语言和主题在应用脚本之前播种到 `localStorage`，那是每个窗口寻找它们的地方。

## 30. Partner Center：丢掉你刚写的东西的四种方式

用 Playwright 填写 Microsoft Store 提交，四个静默失败的事：

1. **上传截图的字段接受一个文件，仅此而已。** 复用同一个 input 会替换前一个而不是添加：连续五次上传留下**一张**截图。每次上传在末尾创建一个新槽，所以该用的 input 是已有截图数的那个。
2. **字段没有无障碍标签，按位置会交叉。** 对个人信息回答是时多出一个字段，所有索引偏移：隐私 URL 落在网站的槽里，网站落在支持的槽里，支持落在**电话号码**的槽里。它们按自己块的文本定位。
3. **`text=Guardar borrador` 找不到按钮；`text="Guardar borrador"` 可以。** 带引号是精确匹配。而那个按钮只在有未保存更改时存在，所以在碰任何东西之前搜索它得到零，看起来它不存在。
4. **价格不自动保存，但看起来会。** 选择它时缺少的警告消失，如果不按保存，重新加载时它还是丢。症状不是错误：是«提交认证»保持灰色，不说六个部分里缺哪个。

**最糟的，是那种看不见的：** 在特性行还没加载完时保存卡片页面**把十一条全删了**，两种语言，没有一条消息。描述和截图还在，所以看起来页面是好的。只有在看整张卡片的照片时才看到。

**教训，一如既往：** 保存一个你不控制的表单之后，重新加载并数里面有什么。保存没报错不意味着它保存了屏幕上有的东西。

## 31. 一个手写的词看起来放进去了但没保存

Store 卡片的关键词在第一次提交里是空的，不得不取消认证来加进去。两个连锁的 bug，两个都无声：

**第一个是明摆着的：那个字段从来没被看过。** 填写卡片时搜索的是已经决定要填的字段，而不是列出页面有什么。关键词住在«附加信息»下面，枚举 `input[type=text]` 时不出现，因为它们不是一个文本字段：是一个 `he-select` 多选，里面带 `freeform`，在 `#search-terms` 里。

**第二个更细。** 打一个词按 Enter，标签出现在字段里，带它的叉和一切。保存，不报任何错，重新加载时**一个都没有**。缺的是移走焦点：Enter 之后按一个 **Tab** 就确认并持久化了。

问题在于文本是手写的这个线索，是用控件自己推荐的一个词测试的：那个确实持久化了。比较能用的和不能用的，比看十遍不能用的更有价值。

**额外附赠，一个直到碍事才看到的限制：** 最多 7 个关键词。测试时多留了一个，卡片变成«不完整»而页面没标任何红。消息「No puede agregar mas de 7 palabras clave」只在读那个块自己的文本时出来。提交按钮保持灰色，和陷阱 30 的价格一样，原因相同：**一个部分的状态在服务器上计算，不在有错误的屏幕上解释**。

## 32. 一个假鼠标不点亮 `:hover`，照片和没有一样

`scripts/ver-ventana.mjs --raton=x,y` 在它自己的注释里说，「没有鼠标就没有 hover」。它发的是手动创建的 `PointerEvent`，那会唤醒一个组件在收到它们时决定的东西（一个改状态的 `onPointerEnter`），但**不唤醒 CSS 的 `:hover` 伪类**，那个只有浏览器的真鼠标点亮。所有用 Tailwind 的 `hover:` 或 `group-hover:` 画的东西在照片里出来**和没人在上面完全一样**，没有错误，没有警告，和好情况没有可见差异。

是在检查 overlay 顶栏悬停时让开时看到的：`--raton` 在栏上的照片和没有鼠标的完全一样。在照片里是真的，在应用里是假的。

工具从内部修不了它：它用命令行 Chrome（`--screenshot`）拍照，那里没有移动指针的地方。所以给它加了 `--servir`，它把屏幕挂载好并写出它的 URL 而不是拍照，真鼠标由外面的 Playwright 用 `page.mouse.move` 放。和陷阱 28 是同一种分工：每个工具做它真正能做的，不能做的，说出来。

## 33. 已修正：唤醒一个隐藏窗口要花约 310 ms

**这个陷阱被写反了几个小时，必须讲讲为什么**，因为方法的错误比数据更有价值。

它说«一个隐藏窗口不启动它的界面»，从那里出来一个托盘菜单的修复，把它显示在屏幕外「唤醒」它。**是假的。** 用来测量的二进制是用 `cargo build --release` 光秃秃编译的，而那个二进制**不带界面**：它从开发服务器找。Vite 关着时，每个窗口显示 Edge 的错误页（«localhost rechazo la conexion»），所以前端的任何计时器都从不触发。人们以为界面不启动，而实际是它不存在。

**真正的事实，用 `pnpm tauri build` 测量，那是把它装进去的：**

| 时刻 | 从按下快捷键起 |
|---|---|
| 屏幕冻结并写入 | 123 ms |
| 窗口显示 | 296 ms |
| **overlay 对通知做出反应** | **606 ms** |
| 8 MB 冻结被读取 | 688 ms |
| **图像绘制，看到的东西** | **689-717 ms** |

也就是说快捷键要 **700 ms**，不是以为的 296，而**最胖的一块是 Rust 显示窗口和里面的浏览器知道之间那 310 ms**。Windows 暂停一个隐藏窗口的浏览器，而 overlay 在截图之间隐藏着以便复用：那是池的代价，没被测量过。读 8 MB 的 BMP 并画它是 83 ms，那不是问题。

## 34. 从另一个线程问窗口一件事会无期限等待，然后挂起应用

0.2.13 一安装就在 Munir 那里冻住了。进程活着，托盘里有它的图标，但**不响应任何一条 Windows 消息**（`Responding=False`），而且有**两个 800x600 的捕获窗口**，这是它们在 `precrear_overlays` 给它们显示器尺寸之前出生的大小：启动停在了一半。

和 0.2.12 相比唯一变的是一个三行的检查，«有截图在进行吗？»，**从另一个线程**做的：

```rust
app.webview_windows().iter().any(|(etiqueta, ventana)| {
    etiqueta.starts_with(OVERLAY_PREFIX) && ventana.is_visible().unwrap_or(false)
})
```

`is_visible()` 看起来是一个无辜的查询，它不是。在 `tauri-runtime-wry` 里，`send_user_message` 看你在哪个线程：如果是主线程，就地处理消息；如果不是，把它发给事件循环并用一个**无期限的 `rx.recv()`** 等回复（宏 `getter!`）。只要循环忙于创建窗口，那个线程就永远卡住，跟着它，后面来的一切也卡住。

**规则：一切碰窗口的事都在主线程做。** 后台线程只用来睡觉；该干活时，把整个工作用 `run_on_main_thread` 发过去，在那里问和做，中间没有通道。

### 而真正失败的是那个检查

发布前测了六次，六次都好。这是一个竞态：取决于线程醒来的确切时刻。**一个依赖时间的东西的一次绿色通过什么都没证明**，而它还是被当成好的接受了。

从那里出来 `scripts/arranca-bien.mjs`：启动应用，等到危险时刻过去，检查它响应并且窗口创建完了。用 `--vueltas=6 --carga` 在机器饱和时做六次，那是这些东西出现的时候。没有任何 `cargo test` 能看到这个：失败不在任何函数里，在两个线程互相等待里。

## 35. 28 ms 是用一块屏幕测的，三块是十倍

winshotx 在 README 和整个网站上宣传，**从按下快捷键到选择出现在屏幕上 28 ms**，对截图工具的 920 ms。这是产品最被捍卫的数字。

在 Munir 的机器上，**三块屏幕**（1920x1080、1080x1920 和 1536x960），同一条路要 **270 ms 环形缓冲区关着，高达 586 ms 开着**。是公布数字的十倍或二十倍，没人看到，因为从没用超过一块屏幕测过。

**原因在 `capture::freeze_all` 里明摆着：** 屏幕在一个 `for` 里拍，一个接一个。写文件确实在下面的 `thread::scope` 里并行了，所以一半工作并行，另一半排队。一块屏幕注意不到；三块付三次。

同时放，每线程一个（每个自己找自己的显示器，因为 `xcap::Monitor` 带一个原始指针，不能在线程间传）：

| 环形缓冲区开着 | 之前 | 现在 |
|---|---|---|
| 冻结 | 157 / 176 / 392 ms | 116-138 ms |
| 到显示选择 | 277 / 378 / **586** ms | **234-272 ms** |

不是 3 倍，因为截图共享视频管道，但**最坏情况从 586 到 272**，尤其是不规则性消失了，那是注意得到的东西：以前同一个快捷键根据时刻要双倍或一半时间。

**对公布数字该做的：** 要么在多屏幕机器上测并说范围，要么说清用什么配置测的。一个只在单显示器上成立的数字，不说明就公布，是一插上第二块就自己碎的数字。

留下一个 `winshotx.exe`，它启动、显示窗口、**里面没有界面**：每个窗口试图从 `http://localhost:1421` 加载它，Vite 服务器。如果那个服务器没起来，窗口显示浏览器错误页，应用看起来半工作着，不说为什么。

## 37. 直接从 asset 协议画冻结比复制到内存**更慢**

overlay 用 `fetch` 拿来冻结，放进一个 blob，再从那里到 `<img>`。看起来是一个傻绕路：每屏 8 MB 从磁盘读、复制到 JavaScript、包起来、解码，而且 `createImageBitmap` 还为了放大镜再解码一次。显而易见的是把 asset 协议的 URL 给 `<img>`，让浏览器一次加载，不经过 JavaScript。

**测了，十二次截图：“显而易见”的路要差不多两倍。**

| | 从快捷键到看到图像 |
|---|---|
| 用 `fetch` 到 blob（现在的） | 460-600 ms |
| 直接从 asset 协议到 `<img>` | **777-1477 ms** |

没有深入数字之外，因为数字已经决定了：**回滚了**。怀疑是 asset 协议的处理器给 `<img>` 的交付比给 `fetch` 差，但那没验证过，这里记下它本来的样子，一个怀疑。

**作为规则有效的是：** 在这个项目里，任何性能想法在留下它之前都测量，即使看起来理所当然会变好。这个看起来理所当然。

## 38. 开机启动保存的是一条**路径**，而那条路径会过期

2026 年 9 月 4 日发现，从 8 月 27 日起就在咬人，没人看到。

Munir 说：*«你得一直更新应用»*，然后发了一张他设置的照片。角落里写着 **Version 0.1.18**。发布的是 0.2.18。

**他机器上的：**

| 哪里 | 版本 | 谁打开它 |
|---|---|---|
| `C:\Apps\Random APPS\winshotx\winshotx.exe` | 0.2.18 | 开始菜单，和注册的卸载器 |
| `%LOCALAPPDATA%\winshotx\winshotx.exe` | **0.1.18** | **开机启动** |

键 `HKCU\...\CurrentVersion\Run\winshotx` 指向第二个。所以他每次开机，启动的都是 0.1.18，0.1.18 检查有没有新版本，找到 0.2.18 并要求更新。更新，安装器写到正确的文件夹，应用从那里重启，而**注册表还指向旧的**。下次开机，又是这样。

**它从哪来的：** `autostart::set_registro` 在按开关的那天写 `std::env::current_exe()`，没人再看过它。只要重装到另一个文件夹（Tauri 向导让你选，Munir 选了一个）就够让那条路径指向一个不再主管的可执行文件。**连开关都不用碰。**

**这带走的东西，是最糟的：** 一周里，他机器上每次重启后跑的应用是 8 月 27 日的。那些天发布的一切让它更快的东西，可能在他抱怨慢的时候并没有在跑。31 号晚上的六个版本是在这里的机器上测的，不是他的。

**修好了**，在 `autostart::revisar_ruta`，它在启动时被调用（不是按任何东西时），如果条目没指向这个可执行文件就纠正它。五个测试，包括他有的那条确切路径。

**规则，适用于任何保存绝对路径的东西：** 一条存在注册表、快捷方式或设置文件里的路径是写它那天的照片。如果某个东西能搬走，就必须在启动时检查它，别指望写它的人让它保持最新。

**还有方法的：** 在相信某人的性能报告之前，**看他装的是哪个版本**。答案在一张已经看过好几次但没读的截图角落里。

### 修复，第一次比病还糟

`revisar_ruta` 的第一个版本光写 `current_exe()`：«如果启动不指向我，就指向我»。半小时后，`scripts/arranca-bien.mjs` 启动了刚编译的 `C:\ct
elease\winshotx.exe` 来检查它启动正常，那个二进制执行了修复，**Munir 的启动就指向了一个测试二进制**。也就是说：为了不让他启动错误副本而写的代码，让他指向了一个更糟的副本，一个甚至没安装的。

**缺的规则：** «我在跑哪个» 和 «哪个是安装的» 是两个不同的问题，`current_exe()` 只回答第一个。第二个由安装器留在卸载键里的 `InstallLocation` 回答。现在只有住在那个文件夹里的可执行文件才动启动项；一个散落的副本（测试的、刚下载的、U 盘里的）不主管任何人的启动。

看到它是因为**碰了注册表之后又读了一遍来检查**。没有那第二遍读，它就会被原样发布，症状会和之前一样，只是换了条路径。

## 41. GIF 比录制快 10%，没人看到

2026 年 9 月 5 日发现，在测 GIF 编码器时，不是在看它时：一个 GIF «就是快»，没人注意到。

GIF 以百分之一秒计时间。每个 33 ms 的帧**单独**舍入到 3 个百分之一，所以三十个 990 ms 的帧出来是 90 个百分之一：一个以 30 fps 录的片段以比实际快 10% 的速度播放。现在舍入从一个帧带到下一个（`gif::Reloj`），总时长就对上了。有一个测试编码十二个帧，重新打开文件并加起延迟。

**规则：** 当某个东西按单位舍入并相加时，舍入会累积。舍入总数并分配差值，不是反过来。

### 以及测同一个编码器出来的三件事

1. **质量 100 每帧要 352 ms；质量 80，46。** 不是质量的问题：是调色板用整个样本训练，而样本随片段大小增长。一千一百万像素在质量 100 下是二十七秒才写任何东西。要限制的是训练**访问**多少像素，不是有多少。
2. **一个跨线程共享的颜色缓存每次出来都不一样。** 答案按«格子»（每个通道的高六位）保存，同一格子的两种颜色答案不同：先到的线程赢。一个编码两次并逐字节比较的测试第一次就抓到了它。一个精确颜色一个格子（16 MB，活到导出结束）按构造是确定性的，而且更忠实：颜色误差从 1,35 降到 1,27 级。
3. **为了和以前的比较，以前的从 git 拉到一个测试模块**（`git show HEAD:ruta > gif_viejo.rs`，`#[cfg(test)] mod gif_viejo;`），测试台用两个编码，测时间、大小和**对原图的颜色误差**（解码 GIF 并逐像素比较）。没有测量的误差，「更快»可能藏着「更差」，而缓存的第一个版本就是。模块结束时删掉了。

| 质量 | 之前 | 现在 |
|---|---|---|
| 50 | 18 ms/帧，误差 2,01 | 6,6 ms/帧，误差 1,26 |
| 80 | 37 ms/帧，误差 1,35 | 8,4 ms/帧，误差 1,27 |
| 100 | **308 ms/帧**，误差 1,54 | 8,2 ms/帧，误差 1,30 |

在 release 里测的，90 个 1280x720 的帧，几乎都是静止的。测试台在 `encode/bench_gif.rs`：`cargo test --release --lib medir_gif -- --ignored --nocapture`。

### 那天测的其他东西，带它们的测试台

| 路径 | 之前 | 现在 | 测试台 |
|---|---|---|---|

## 42. 飞到 overlay 的 8 MB、睡着的窗口和换 DPI 的窗口

Munir，2026 年 9 月 5 日：*«尤其是想截图时的加载时间，还有去掉开头那个加载，那看起来很差»*。带«Preparando la captura»的暗屏每次拍摄时可见将近半秒。

**怎么测的，终于测对了：** 应用内部一个计时器（`crono.rs`，用 `--crono` 打开，把每个阶段写到 `%TEMP%\winshotx\crono.log`，前端的通过 `crono_marca` 命令到达），一个从外面的触发器（`winshotx.exe --capture` 和 `--cancel`，单实例把它传给在跑的那个）和 `scripts/cronometrar-atajo.mjs`，它重复六次截图并取中位数。三块屏幕，第一次测量说：

| 阶段 | 从快捷键起的 ms |
|---|---|
| 屏幕冻结 | 110 |
| 窗口显示（带加载屏） | 140-180 |
| 浏览器收到通知 | 205-290，有时 450 |
| **每屏 8 MB 到达浏览器** | **550-590** |
| 图像绘制 | 590 |

**最胖的一块不是浏览器在反应：是给它送每屏 8 MB。** WebView2 服务文件和 IPC 响应的协议大约 70-90 MB 每秒，三个窗口每个要 8 MB 就是 24 MB 排队。用快速 PNG（`png::to_bytes`，每屏 28 ms，并行）每个是两三兆字节，80 ms 到达。冻结不再碰磁盘：它从内存通过 IPC 走（`freeze_png`），未压缩的 BMP 作后备。

**第二件：** 通知有时要 280 ms 才到浏览器。Chromium 把一个看不见的窗口当作«后台»，而 overlay 停在屏幕外。开关 `--disable-renderer-backgrounding --disable-backgrounding-occluded-windows --disable-background-timer-throttling` 避免它，**但它们必须在所有窗口里，包括 `tauri.conf.json` 的 `main`**：WebView2 共享一个浏览器进程，由第一个窗口配置它；一个请求其他参数的窗口没有 webview，出来是白的。这就是第一次尝试时发生的事（陷阱 33），也是它被放弃的原因。参数在七个窗口里，通知 10 ms 到达。

**第三件，是去掉加载屏的那件：** 窗口不再在冻结时显示。把图像送到停放的窗口，当前端画好了它通知（`overlay_listo`，带截图号以忽略已取消的截图的通知），Rust 用一次调用把它带到位置（`SetWindowPos` 配 `SWP_SHOWWINDOW`）。如果一个 overlay 在 900 ms 内不通知，照样显示它，为了能看到它的错误并用 Escape 退出。

**还有优先级：** 先冻结鼠标所在的那块屏幕并只把它的图像发过去；其他在后面。**这一切在另一个线程里**：第一个版本在主线程做，而给每个窗口的通知走那个线程的消息循环，所以它在队列里等着，同时另外两块在冻结。53 ms 冻结好，它的浏览器 131 ms 才知道：优先级没用。

### 测这个时出来的两个陷阱

1. **`pnpm tauri build` 之后跑 `cargo test` 会留下一个没有界面的二进制。** 为了省时间把它们串起来了，测试重新编译了 `winshotx.exe` 但没有 `custom-protocol` 特性，那是把 `dist/` 塞进去的。计时器看不到前端的任何标记，窗口靠 900 ms 的救援出来。通过拍窗口看到了（陷阱 36，又一次）：Edge 的错误页。**测试在 build 之前，或者 build 重做。** `scripts/fotografiar-ventanas.ps1` 做那张照片而不碰任何东西。

   **从 2026 年 9 月 9 日起，这不再依赖记得。** 没有界面的二进制不用打开就能认出来：它轻大约 200 KB，而且**里面不带 `dist/assets` 的文件名**，好的二进制里那些是明文，尽管它们的内容是压缩的（6.354.944 字节对 0.2.23 里的 6.561.280）。`scripts/msix.mjs` 在打包前检查它并停下来，那正是最贵的地方：为 Store 打包那个二进制就是已经花了一轮的«Display error page at launch»拒绝。

## 43. Windows Defender 把 winshotx 从它自己作者的电脑上删掉了

Munir，2026 年 9 月 7 日：*«为什么我没装 winshotx？»*。没人卸载它：**Windows Defender 在 9 月 6 日 9:44 把它隔离了**，报 `Trojan:Win32/Wacatac.C!ml`，Defender 的自动学习模型对一个没有数字签名的可执行文件的通用判决。

而且它不只删了 `.exe`。检测列表，用 PowerShell 拉出来的，是这样的：

```
file:_C:\Apps\Random APPS\winshotx\winshotx.exe
file:_...\Start Menu\Programs\winshotx.lnk
file:_...\Escritorio\winshotx.lnk
process:_pid:16428
regkey:_HKCU\...\CurrentVersion\Run\winshotx
regkey:_HKCU\...\CurrentVersion\Uninstall\winshotx
```

也就是说：杀了进程，删了二进制、两个快捷方式、开机启动和**“已安装应用”的条目**。文件夹里只剩一个孤立的 `uninstall.exe`。所以电脑看起来不是“winshotx 坏了”，而是**干净的**，像从没装过一样：没什么可看的。

### 怎么确认是这个而不是别的

三条命令，不需要管理员权限，按这个顺序：

```powershell
Get-MpThreatDetection | Where-Object { $_.Resources -match 'winshot' } |
  Select-Object InitialDetectionTime, Resources
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Windows Defender/Operational'; Id=1116,1117} |
  Where-Object { $_.Message -match 'winshot' } | Select-Object -First 1 -ExpandProperty Message
& 'C:\Program Files\Windows Defender\MpCmdRun.exe' -Scan -ScanType 3 -File <ruta al exe>
```

第一个说**是否**有检测以及它带走了什么；第二个说**用什么名字**（消息出来时重音是坏的，但 `ThreatName` 读得清）；第三个说**今天**它是否还在检测。从隔离区恢复和看排除项需要管理员；上面三条不需要。

### 重要的：今天它不再跳了

扫描同一个二进制和 9 月 7 日发布的 0.2.23 安装包，用当天的签名：`found no threats`。也就是说那是一次**云模型的临时误报**（`!ml` 和来源 `FastPath`），之后被 Microsoft 纠正了，没人申诉。重装就行：

```
winshotx_0.2.23_x64-setup.exe /S /D=C:\Apps\Random APPS\winshotx
```

`/D=` 放**最后且不带引号**，即使路径带空格；NSIS 原样拿行的剩下部分。

### 这对产品意味着什么，那才是真正疼的

那个安装包在事情发生时已经有 **30 次下载**。那 30 个人里任何一个都可能遇到同样的事，而没人会报告：他们会以为应用是病毒，或者甚至不会发现它消失了。**一个没有签名的 Rust `.exe` 是 Wacatac 的肉**，只要不签名，每个版本都会再发生。

三条出路，从最不彻底到最彻底：

1. **发生时报它**，免费，三天，在 `microsoft.com/wdsi/filesubmission` 作为软件开发者。为所有人修受影响的版本，不只为一个。
2. **签二进制。** Azure Trusted Signing 是 Microsoft 的，一个验证过的个人开发者够得着；一个经典 EV 证书贵好几倍。这是唯一从根上为 GitHub 安装包和 winget 去掉问题的方法。
3. **Microsoft Store**，已经在进行中：MSIX 由 Microsoft 签名，所以那条路不可能发生检测。见发布到 Store 的记忆。

同时，诚实的警告：如果有人说“winshotx 从我这儿消失了”，第一个问题不是他装的什么版本，是 `Get-MpThreatDetection`。

## 44. 正好挡住你正在看的东西：角落里的放大镜和屏幕外的栏

Munir，2026 年 9 月 9 日：*«当你截屏幕的一个角落时看不到你在截什么»* 和 *«当你一次点击全选而且开着栏的模式时，编辑复制等的栏不出现»*。两个抱怨，下面同一个 bug：**一个放在固定位置、只为了不出去而被裁剪的部件。**

### 放大镜放在它要放大的像素上面

它总是在光标下方和右方 18 px，为了不出去被夹住：

```js
left={clamp(cursor.x + 18, 0, window.innerWidth - 148)}
top={clamp(cursor.y + 18, 0, window.innerHeight - 168)}
```

光标在 1440x900 屏幕的右下角，那是 `left 1292, top 732`：放大镜占从那里到 1440x900，**光标（1400, 860）落在里面**。也就是说用来看到确切像素的工具放在了那个像素上面。夹住避免它出去，但不避免它挡住。

现在它**换边**，那是栏已经在做的：右边放不下就去光标左边，下面放不下就去上面（`sitioDeLaLupa`）。

### 栏存在，带它的按钮，一个像素都看不见

裁剪占满整个屏幕时下面放不下（`y + alto + 62 > pantalla`），所以它翻转并放在 `top: active.y - 10`，也就是 **-10**。翻转后，那个 `top` 是它的下边缘：栏整个在负数里，在 -62 和 -10 之间。

正确说它的测试不是«DOM 里有一个 Copiar 按钮»（有的），而是**它在哪里**：读它的 `top`，如果翻转了就减掉高度，要求结果落在屏幕内。现在，当下面和上面都放不下时，栏放进裁剪**里面**，贴它的下边缘（`sitioDeLaBarra`）。

### 还有第三件，是藏起另外两件的那件

开着«全屏»时，点击把屏幕送到剪贴板并关闭，**即使选的配置是带栏的那个**。这是故意写的（«一次点击就是一次点击»），但 `Ctrl+A`，做完全一样的事，却显示了栏。两条到同一个地方的路不能在两个不同的地方结束：现在两条都选择，让人决定。

### 测试台到不了 overlay：用 Vitest

`pnpm ver --overlay=x.png --raton=700,450` **不移动放大镜**。用 `--dom` 验证了：它停在 `left: 18px; top: 18px`，也就是光标在 0,0，尽管发到了中间。脚本注入的假鼠标那个组件不接收，用更长的等待或发好几次也修不了，因为在虚拟时间下计时器全部在开头触发，在冻结屏幕解码之前。

能移动鼠标的地方是 **`SelectionCanvas.test.tsx`**（Vitest + happy-dom）：那里真正触发 `pointerMove` 并读放大镜的 `style.left`。这个陷阱的六个新测试住在那里，而且它们在碰代码之前先变红了。对栏照片确实有用（`--seleccion=0,0,1440,900`），事实上是照片揭示了真正的问题不是点击，是栏落在了外面。

## 45. 录制的四件事，没人看到因为都不报错

2026 年 9 月 10 日从上到下读 `recorder.rs` 时出来的，带着问题«录制的人看到什么？»。四件都通过了所有测试。

### 栏的时钟在暂停时还在走

`RecordingState::elapsed_ms` 减 `paused_ms`，而 `paused_ms` **只在恢复时更新**。暂停开着时时钟继续涨，恢复时向后跳一下。看栏的人看到一个在数没在录的时间的计时器。现在 `tiempo_grabado`（在 `state.rs`，纯函数且有测试）也减掉进行中的暂停。

### 声音在暂停时还在写，视频出来不同步

图像捕获看暂停标志，不发帧。**声音捕获不看它**：片段继续通过通道到达，恢复时全部写到 `audio.pcm`。图像从它的时间戳里减掉暂停，声音没有，所以导出时，`pista_de_audio` 按图像的时间裁文件，把暂停的声音也带走了：**暂停 N 秒后，视频比音频快 N 秒**。现在 `audio::empezar` 接收同样的标志，继续排空 Windows 的缓冲区（否则它会满并报不连续）但丢掉读到的，采样计数器不前进：对文件和编码器来说暂停没发生过。

### 从快捷键停止冻结整个应用

`recorder::stop` 用 `join()` 等写线程，而写线程最后要给所有帧做缩略图：每分钟录制要几秒。全局快捷键在主线程跑（陷阱 1），所以在那些秒里整个应用卡住，包括栏，甚至不显示在保存。现在 `stop` 拿出状态，给栏发一个带 `saving` 的最后 tick 就返回；所有耗时的在另一个线程里。栏停在«Guardando…»而且**不倒退**，尽管两个线程之间的竞态让一个旧 ticker 的 tick 在后面到达。

### 关掉编辑器时，录制丢了

`open_editor_after_recording` 为假时把会话留在 `%TEMP%\winshotx\sessions`，没有文件，没有通知，没有任何屏幕能回到它。设置说«留着保存然后继续你的事»。24 小时后启动时的清理删掉它。现在 `entregar` 自己用 `peticion_por_defecto`（和打开编辑器时一样的值）导出到设置的文件夹，如果快门开着就响。

### 以及那个不是 bug 但遮住了四个的：看不到正在录制

开始录制时 overlay 关闭，没有留下一个像素说正在录哪个区域。`platform/marco.rs` 用手放四个 Windows 窗口（没有 webview，每个要几十兆字节）两像素**在外面**，点击穿过它们，它们不抢焦点。在外面是让它们留在视频外的东西。它们在屏幕外用 `PrintWindow` 测试，那要求窗口在内存里画自己：这样真正检查颜色而不在任何人的桌面上出现任何东西。

## 46. 没有烧录光标时，静止屏幕不发帧：鼠标轨迹有空洞

导出时画的指针出来«在它不该在的地方»（Munir，2026 年 9 月 10 日）。鼠标轨迹是**每个从 Windows Graphics Capture 收到的帧**记一次，而 WGC 只在屏幕变化时给一帧。光标烧在图像里时，动鼠标改变屏幕，帧到达；**没有烧录光标时，在静止屏幕上动鼠标什么都不改变**，没有帧到达，轨迹恰好在鼠标移动时没有点。导出时，指针钉在最后一个点然后跳一下。

**修复：** 鼠标从它自己的线程每 16 ms 看一次（`anotador::Muestreador`），和帧用**同一个时钟零点**（`CaptureFlags::start`，共享），暂停时不看（恢复时时间被减掉，中间取的点会倒退）。在 `%TEMP%\winshotx\sessions\<id>\session.json` 里看得到：以前 `cursor` 的点之间有超过一秒的跳跃；现在 16 ms，没有帧在中间。

**还有抱怨的后半部分，«画质差»：** 指针是手画的多边形。现在从 Windows 读当前设置的光标的真实图像（`record/punteros.rs`：`GetIconInfo` 和 `GetDIBits`；彩色的带透明，单色的，那是两个叠起来的掩码，也读）并缩放粘贴它。注意：从一个没有窗口的进程调用 `LoadCursorW(IDC_ARROW)` 返回**单色**版本，而 `GetCursorInfo` 在打字时返回空光标，所以测试按固定标识符加载光标，并容忍眼前没有任何光标。
